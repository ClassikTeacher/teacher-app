# Ревью и анализ PRODUCT-SPEC.md (v0.1)

> **Дата:** 2026-10-19. **Объект:** `PRODUCT-SPEC.md` целиком (разделы 1–12) с ответами в столбце «ответ» раздела 12.
> Сам документ не правился. Здесь — выводы, последствия ответов, найденные противоречия, новые вопросы и чек-лист правок.
> «В1…В20» — вопросы раздела 12. Коды правил (`CAL-01` и т. п.) — из спецификации.

## 1. Главное

**Общая оценка.** Документ зрелый для v0.1: есть принципы, коды правил, диаграммы состояний, ограничения Telegram учтены и проверены, ключевые технические решения выбраны правильно (EXCLUDE-ограничение для пересечений, transactional outbox, таблица уведомлений как источник истины, модульный монолит, флаги фич как основа будущих тарифов). По нему можно начинать планирование.

**Что требует действий до начала разработки:**

1. **Ответы раздела 12 противоречат текущему тексту в четырёх местах**, их надо внести, а не держать рядом: один StudyBot ↔ разные боты для ученика и родителя (В4); ручное подтверждение заявок с удержанием ↔ автоподтверждение по умолчанию (В7); «Календарь» как фича ↔ ядро (В1); четверти и годовые ↔ не нужны в MVP (В10). Всего ответы затрагивают около 30 мест документа (чек-лист в разделе 8).
2. **Модель владения данными (В6) надо зафиксировать как принцип**, а не держать в «нужно продумать». Текущая модель данных уже почти соответствует ответу (владелец — учитель, ученик — участник); не хватает явной формулировки, трёх денормализованных колонок и двух решений (квота на сдачи, блокировка учителя). Разбор — в разделе 3.
3. **Объём MVP великоват для «локального теста» (В18):** 42 use-case, 7 вех. Часть сценариев можно перенести на этап 2 без потери сути — список в разделе 6.
4. **Внутренние противоречия и пробелы**, не связанные с ответами: отмена «идущего» занятия (LES-03 vs UC-20), серия без индивидуального ученика в модели данных, срок ДЗ «к следующему занятию» при нескольких адресатах, номер занятия для групповых, отсутствующий пункт меню «Мои учителя». Полный список — раздел 4.
5. **Ответы В2, В7, В8, В13 решают принцип, но не механику** — остались развилки, которые надо закрыть (раздел 7, вопросы 21–32).

### 2.2 Разбор ключевых решений

#### В1. Календарь — ядро

- Из каталога фич уходит `calendar`. В ядро (5.3.1) добавляются: окна, просмотр недели и занятости, серии, личные блоки учителя, «Сегодня / Завтра / Неделя».
- У `calendar.open_booking`, `calendar.google`, `calendar.ics` зависимость `calendar` снимается. Имена можно оставить (префикс — просто группа) либо переименовать в `booking`, `google_calendar`, `ics`.
- Пункт «💡 Решение для подтверждения ❓» в 5.3.1 удаляется целиком.

#### В2. Отмена учеником и родителем по умолчанию

Настройки учителя (новые поля `teacher_profile`): `student_can_cancel` (по умолчанию `true`), `parent_can_cancel` (по умолчанию `true`), общий `student_cancel_cutoff_hours` (CNL-07) — действует и для родителя.

Что дописать:

- `CNL-02`: родитель отменяет занятие ребёнка, если учитель не отключил; при отключении бот предлагает «Написать учителю» (как в CNL-07).
- `CNL-03`: на групповом занятии родитель, как и ученик, не отменяет, а сообщает об отсутствии ребёнка.
- 5.13.1 `lesson.cancelled`: получатели — «все остальные стороны»: при отмене родителем уведомляются учитель и ученик, остальные родители — копией.
- Матрица 3.7: Ученик — ✅ (свои; учитель может отключить), Родитель — ✅ (за ребёнка; учитель может отключить). Убрать 💡 и ❓ из 3.6.
- **Массовая отмена родителем** (ребёнок заболел на неделю) сейчас в матрице «—». Логично дать родителю те же режимы, что ученику, в контексте выбранного ребёнка (вопрос 25).

#### В4. Родителей добавляет только учитель; боты разные

**Интерпретация:** вместо одного StudyBot с переключателем ролей — два бота: **StudentBot** (ученик) и **ParentBot** (родитель). Итого четыре бота: AuthBot, StaffBot, StudentBot, ParentBot. Если имелось в виду другое (например, только разные меню внутри одного бота) — вопрос 21.

Плюсы: нет переключателя ролей, меню проще, у каждого бота свой лимит отправки, родитель никогда не увидит ученических команд, аккаунт «взрослый ученик + родитель» не требует спецобработки. Цена: четвёртый токен и набор обработчиков, больше e2e-тестов, человек «учитель + родитель» живёт в трёх ботах.

Что меняется:

- Глоссарий, 3.1, 4.2 (таблица ботов), 4.3 (вариант A: два личных чата), 4.4 (меню раздельно, без переключателя роли).
- Приглашение родителя — deep link на ParentBot; карточку пересылает учитель (у него уже есть контакт родителя).
- 5.13: у каждого уведомления — бот доставки; копии родителям уходят через ParentBot.
- 8.2: `bot_chat.bot`, `notification.bot`, `telegram_file_cache.bot` → `auth | staff | student | parent`. Файл проверки, который уходит ученику и копией родителю, загружается дважды (по одному `file_id` на бота) — так и было по правилу 4.1.
- 7.4: четыре входа в Telegram gateway; `libs/telegram/` — четыре бота; вебхук `POST /tg/{bot}/webhook` для четырёх значений.

**«Именно учитель добавляет родителей»:** убрать 💡-право ученика приглашать родителя (3.5, 3.7, 5.4.3, UC-11 — актор только учитель). Пункт меню «Родители» у ученика оставить **только для просмотра**: ученик должен видеть, кто получает копии его данных (прозрачность), но не управлять списком.

#### В6. После ухода и владение данными

Решение по доступу: ушедший ученик — история только для чтения (как в 5.8.4); заблокированный — ничего. Второе следует из статуса `blocked`, но стоит написать явно в 5.8.4 и ACC-01: блокировка перекрывает и «Архив».

Архитектурная часть («данные привязываются к занятию и учителю») разобрана в разделе 3.

#### В7. Заявки без подтверждения по умолчанию

Это переворачивает 5.5.5 и UC-16/17: основной поток — не «заявка → удержание → решение учителя», а «ученик выбрал слот → занятие создано». Предлагаемая формулировка:

- **Режим «без подтверждения» (по умолчанию):** выбор слота создаёт занятие в одной транзакции (занятость всех участников, `CAL-01`). Учитель получает `lesson.created` с кнопками «ОК» и «Отменить» (с причиной, как обычная отмена). Удержаний нет, `booking_request` не создаётся.
- **Режим «с подтверждением» (настройка учителя `booking_confirmation = manual`):** текущий поток с удержанием, `CAL-10`, истечением, «Предложить другое время».
- **Лимиты в режиме без подтверждения:** минимальный срок до начала, горизонт и ограничение числа самостоятельно поставленных будущих занятий — иначе один ученик может занять весь открытый календарь. Ответ «2 заявки на сло… до подтверждения» прочитан как «не больше 2 активных заявок у ученика» (режим с подтверждением). Для режима без подтверждения аналогичный лимит надо назвать отдельно — вопрос 22.
- **Перенос учеником при открытом календаре** (5.7.4): в режиме без подтверждения логично тоже применять сразу, с уведомлением учителю и кнопкой «Не могу в это время» (зеркально переносу учителем). Нужно решение — вопрос 24.
- 5.13.1: `booking.requested` / `booking.decided` — только для режима с подтверждением; у `lesson.created` добавить получателя «учитель, если занятие создал ученик».

#### В8. Текст по умолчанию при переносе

- Новое поле профиля: `teacher_profile.default_notice_text` (название условное). Платформенный шаблон предзаполнен; в анкете онбординга (5.1.2) — отдельный шаг «Текст, который получат ученики при отмене или переносе без комментария».
- `CNL-09`: перенос учителем — комментарий не обязателен; при пустом подставляется `default_notice_text`. Снять ❓.
- **Развилка для отмены.** Ответ называет поле «текст отмены занятия». Если оно подставляется и при отмене без выбора причины, `CNL-01` («пустое сообщение не принимается») формально выполняется, но «тихие отмены» возвращаются в мягкой форме: ученик всегда получает один и тот же дежурный текст. Рекомендация: при отмене это поле — первый, предвыбранный шаблон в списке 5.7.2, который учитель подтверждает одним нажатием; автоподстановка — только при переносе. Вопрос 23.
- 5.7.2 можно упростить: текст по умолчанию = шаблон №1 с пометкой «по умолчанию», отдельная сущность не нужна.

#### В10. Без четвертей в MVP

Убираются: учебные периоды (глоссарий, 4.4 «учебные периоды», 5.11.2 «Учебные периоды», таблица `academic_period`, `GET|PUT /academic-periods`), расчёт четвертных и годовых (1.2, описание `journal.school` в 5.3.2, 5.11.2 «Расчёты»: прогноз четвертной, годовая, замена прогнозов фактическими), «прогноз четвертной» в 5.12, из M6 — «учебные периоды, расчёты».

Остаётся: средний балл за **произвольный период** (месяц, диапазон дат) с весами категорий — он нужен отчёту (5.12) и не требует четвертей. Категории «четвертная (фактическая)» и «годовая (фактическая)» можно оставить как обычные метки записи, без вычислений.

Шкала школьного журнала в MVP — фиксированная 10-балльная; варианты (5-, 12-балльная, своя числовая) — этап 2. Таблица `grade_scale` остаётся ради кастомного журнала.

#### В11. Журналы по предметам

Подтверждено. Чтобы «новый предмет → новые журналы» не плодил дубли из-за опечаток («Математика» / «математика»), предмет должен быть справочным значением из списка учителя (`teacher_profile.subjects[]`), а не свободным текстом в `teacher_student.subjects[]`, `lesson.subject`, `journal.subject`. Уникальность: `journal (teacher_student_id, subject, type)`; журналы создаются лениво — при добавлении предмета к связи или при первой записи. Вопрос 31.

#### В12. Офлайн-учеников нет

Упрощения: `account.telegram_user_id` становится `NOT NULL` (из принципа 1.4.7 исчезает исключение), удаляются `invite.offline_student`, способы «Офлайн-карточка» и «Через родителя» в 5.4.2, `student_profile.delivery_via_parent`, NTF-04 как режим (кроме случая 403, см. ниже), 💡 в 4.3. Поле `consent.on_behalf_of` остаётся только если принят поток В13.

Ограничения обходного пути «родитель регистрируется как ученик», которые стоит записать явно:

- По `PPL-02` один Telegram-аккаунт — один аккаунт ученика: родитель двух младших детей без Telegram сможет завести только одного.
- Такой аккаунт — ученик с точки зрения системы: согласие родителя на уход (LINK-02) к нему не применяется, имя аккаунта — имя ребёнка.
- NTF-09: случай «ученик заблокировал бота → сообщения уходят родителю» можно оставить, он не про офлайн-учеников.

#### В13. Согласие родителя за несовершеннолетнего

Ответ фиксирует принцип (родитель — сторона, дающая согласие), но не механику: система должна знать, что ученик несовершеннолетний, и обеспечить согласие **до** активации связи. Рекомендуемый поток, который хорошо ложится на В4 («родителей добавляет учитель») и В12:

1. Учитель при добавлении ученика выбирает «школьник» или «взрослый ученик» (признак хранится в `teacher_student` или `student_profile`).
2. Для школьника ссылка-приглашение ведёт в **ParentBot**: родитель проходит онбординг, подтверждает согласие на обработку данных ребёнка (`consent` с `on_behalf_of`) и указывает имя ребёнка.
3. ParentBot выдаёт родителю ссылку для StudentBot; родитель пересылает её ребёнку или открывает сам (обходной путь В12).
4. Семейная связь создаётся сразу; связь учитель–ученик становится `active` только после согласия родителя.

Для взрослого ученика — текущий поток 5.4.2. Групповая ссылка и QR (если останутся в MVP) для школьников должны давать `pending` до согласия родителя. Юридическая проверка — к релизу (В18), но поток лучше заложить сейчас: переделывать онбординг дороже всего. Вопрос 26.

#### В16. Вход только по username

Убрать 💡-альтернативу с QR и кнопкой из 5.2. Две оговорки: username в Telegram необязателен и может меняться. Предложение: AuthBot при онбординге staff проверяет наличие username и просит его установить; username обновляется при каждом апдейте (3.1 это уже предусматривает). Устаревший username, перехваченный другим человеком, приводит только к лишнему уведомлению «кто-то запросил вход» у старого владельца: код уходит в чат аккаунта, доступ не утекает, AUTH-01 скрывает факт существования.

Поскольку веб — этап 2, весь блок AUTH (коды, сессии, `/login`, `/sessions`, `/logout_all`, `web_session`) можно перенести туда же; AuthBot в MVP останется ботом онбординга. Вопрос 29.

#### В20. Монетизация

Решение «платят только учителя» подтверждает принцип 5.3.3 «возможности учеников следуют за фичами учителя»: ученик и родитель никогда не упираются в платное ограничение. Модель `feature` / `account_feature` подходит под любую из трёх схем; на этапе 2 достаточно добавить сущность «тариф = набор значений фич и лимитов». Сейчас ничего не менять.

## 3. Владение данными (по вопросу 6)

**Что есть сейчас.** Модель данных уже почти соответствует ответу: `lesson`, `assignment`, `material`, `collection`, `study_group`, `report` имеют `teacher_id`; журнал привязан к связи учитель–ученик (`journal.teacher_student_id`), а значит к учителю; ученик фигурирует как участник (`lesson_participant`, `assignment_target`, `submission.student_id`). Иными словами, **учитель — владелец (tenant) учебных данных, ученик — субъект и участник**.

**Что предлагается зафиксировать** (новый принцип в 1.4 и абзац в разделе 8):

1. Каждая учебная запись принадлежит ровно одному учителю. Ученик не владеет записями — у него **производное право чтения** через участие (участник занятия, адресат задания, субъект журнала).
2. Право чтения вычисляется при каждом запросе из трёх вещей: статус аккаунта ученика (`blocked` → ничего), статус связи (`active` → полный доступ; `ended` → только чтение «Архива», новые выдачи не приходят), факт участия в записи.
3. Денормализовать `teacher_id` (и `student_id`, где его нет) в `journal`, `grade_entry`, `submission`, `submission_review`, `file` (для сдач — `owner_teacher_id`). Это упрощает проверки прав, квоты и будущий Row-Level Security (10.1), а запрос «всё по ученику у учителя» становится одним фильтром.
4. **Квота хранилища.** Файлы сдач загружает ученик, но платит учитель (В20) — логично считать сдачи в квоту учителя с отдельным подлимитом «на ученика». Сейчас в спецификации это не определено. Вопрос 27.
5. **Обезличивание (10.2).** При удалении ученика по запросу записи учителя остаются с «Удалённым пользователем», но файлы сдач — работы самого ученика; их судьбу определить вместе с политикой (В18).
6. **Блокировка или уход учителя.** Симметричный случай не описан: что видит ученик, если учитель заблокирован (ACC-02 закрывает только занятия)? Предложение: история остаётся в «Архиве» ученика, материалы закрываются, журналы — только чтение. Вопрос 28.

Отдельный вывод: раз владелец — учитель, то **«Архив» ученика — это проекция, а не копия**. Снимки нужны только там, где они уже предусмотрены: отчёт (`report.snapshot`).

## 5. Технические замечания

- **EXCLUDE и дружелюбная ошибка.** Нарушение ограничения приходит как `23P01 exclusion_violation`; из текста ошибки неудобно надёжно доставать, у кого именно конфликт. Делать предварительный `SELECT` по занятости для понятного сообщения (`CAL-06`), а на ограничение полагаться как на защиту от гонок. Стоит записать в 7.5.
- **Серии и летнее время.** `rrule` (rrule.js) работает с «плавающим» временем, поддержка `tzid` частичная. Разворачивать правило в часовом поясе учителя через Luxon, а RRULE хранить как формат; тесты на переход DST (10.6) — обязательно.
- **UUID v7.** PostgreSQL 16/17 не генерирует v7 (появилось в 18) — генерировать в приложении; записать в раздел 8.
- **ClamAV** в Docker Compose — порядка 1–2 ГБ памяти и долгая первая загрузка баз. Для локального теста (В18) сделать шаг антивируса подключаемым (`scan_status = skipped`), пайплайн 7.5 не менять.
- **Партиционирование `audit_log` и журнала доставки по месяцам** на объёмах MVP (10.3) преждевременно; оставить как план, не как требование M1.
- **Очереди.** Redis + BullMQ оправданы (Redis всё равно нужен для сессий ботов). Альтернатива для одного сервера — `pg-boss` поверх PostgreSQL: минус одна зависимость в критическом пути уведомлений; упомянуть как вариант в 7.3.
- **grammY на вебхуках:** апдейты одного чата могут приходить параллельно; многошаговым диалогам нужна сериализация по `chat_id` (в grammY — `sequentialize` из runner или своя блокировка в Redis). Добавить в 7.5 «Диалоги в ботах».
- **Четыре бота в одном процессе (В4)** — спецификация уже закладывает «одна кодовая база, один шлюз»; добавляется только четвёртый токен и префикс вебхука.
- **`notification` как источник истины + BullMQ** — правильно. Зафиксировать порядок: статус `sending` пишется в PostgreSQL до вызова Telegram, задача идемпотентна по `dedupe_key`; тогда падение между отправкой и записью даёт «как минимум один раз», а повтор ловится по ключу.

## 6. Объём MVP: кандидаты на перенос

Ответ В18 («локальный тест») позволяет сжать MVP. Критерий: убираем то, что не нужно для проверки ядра «расписание без накладок → отмены с причиной → ДЗ → журнал → отчёт родителю».

Оставить несмотря на цену: массовая отмена (главная боль «заболел»), утренняя сводка, серии с паузой, ICS (дёшево).
